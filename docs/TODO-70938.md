## Group 1 — Fixable, we have the data (~34 packets)

### 1.1 `SMSG_HEALTH_UPDATE` — 6 packets — 145 bytes unread

Wire `0x47017F`, length **161**, handler stops at position 16.

The handler reads the single-object form: `[Guid][u32 ClassicUnknown][u32 Health][u8 pad]`
= 16 bytes. A 161-byte packet under this opcode is **not** a health update —
Forever reuses the opcode for a batch form. This is the largest single unread
tail after the auth/account packets.

**To do:** find the batch layout. Needs either the Forever emulator's
`SMSG_HEALTH_UPDATE` builder or a second capture where the packet is smaller.

### `SMSG_GUILD_ROSTER` — 61 packets — no longer throws, but reads the wrong bytes

The `FormatFloat` guard (patch 0004) stopped the exception. The underlying
layout problem is **untouched**:

```
WowPacketParserModule.V9_0_1_36216.Parsers.GuildHandler.HandleGuildRoster  GuildHandler.cs:64
  -> WowPacketParserModule.Substructures.MythicPlusHandler.ReadDungeonScoreSummary
```

Forever 1.60.1 has **no Mythic+**. `HandleGuildRoster` still calls the retail
`ReadDungeonScoreSummary`, so those bytes are read as a structure that does not
exist in this client. The packets now close cleanly, which means the reader is
consuming the right *number* of bytes but interpreting them as the wrong thing.

This is the **only place where the parser silently produces wrong data**.
Everywhere else it either reads correctly or admits it did not finish.

**To do:** write a Forever-specific guild-roster field list and stop calling
the Mythic+ reader for this build.
